# 项目负责人执行、进度跟踪与验收模板

## 一、开工前填写

| 信息 | 填写 |
| --- | --- |
| 项目负责人/校方接口人 | 待填写 |
| A 后端与平台 / GitHub 用户名 | 待认领 |
| B 小程序 / GitHub 用户名 | 待认领 |
| C 后台 / GitHub 用户名 | 待认领 |
| 开工日、每天可投入时长、验收日 | 待确认；计划按 7 个工作日、每人每天约 6–8 小时 |
| 仓库写权限和 PR 评审方式 | 待确认；无写权限使用 fork+PR |
| 微信开发者工具、测试号/AppID、真机 | 待核验，不可用立即登记 |
| 测试服务器、PostgreSQL、域名、HTTPS | 待核验；最低先用独立本地环境 |
| 学校材料提供人和审核人 | 待填写；没有正式资料先用合成数据 |
| 负责人每天检查时间 | 待填写 |

## 二、角色认领后的第一条 Issue 更新

```text
我认领 A / B / C；GitHub 用户名：
可投入的日期和时段：
已阅读：README、共同约定、系统架构与契约、角色任务书、验收用例。
开发环境和缺少的工具：
我的分支 / Draft PR：
我今天将交付：
目前最可能阻塞的事项：
```

负责人确认：三个角色都有人，避免重复领取；确保每人能访问仓库、能提交 PR，并知道不能把真实数据提交到公开仓库。A 不应等第 1 天所有工作完成后才给出接口；B/C 用冻结的接口 mock 同步进行。

## 三、每天怎么问，怎么判断

每天只问五项：1）今天具体交了什么；2）在哪个 PR 或 commit；3）怎样操作可以看到；4）跑了哪些测试、结果怎样；5）谁有阻塞、何时需要决定。负责人现场点一次关键路径。截图只能辅助判断；持续运行和接口权限需依据测试记录。

| 时点 | 负责人实际操作 | 必须收到的证据 |
| --- | --- | --- |
| 第 1 天晚 | 三人各启动工程；检查契约和依赖 | API/DB 启动、小程序导入、后台打开的记录；角色与权限矩阵；若工具不可用列阻塞 |
| 第 2 天晚 | 测登录、后台创建草稿、公开列表与详情 | 后台和 API 请求记录、公开端不展示草稿的证据 |
| 第 3 天晚 | 亲自分别用编辑和审核账号完成送审、审核、发布 | 两账号操作录屏或现场操作；公开端看到已发布且不能看到草稿 |
| 第 4 天晚 | 用虚构数据做测试咨询，切换账号查看 | 成功/失败和重复提交记录、无权限角色被拒记录 |
| 第 5 天晚 | 阅读缺陷清单并冻结 P0 范围 | 已合并 PR、每个缺陷的等级/负责人/修复时限 |
| 第 6 天晚 | 观看部署、备份恢复和权限检查 | 自动化测试、隔离库恢复及回滚的实际证据 |
| 第 7 天 | 从新环境按说明验收固定 commit | 全部 P0 用例、未通过项及决定；版本与交付物清单 |

## 四、缺陷表模板

```text
编号：BUG-001
级别：阻断 / 高 / 中 / 低
发现版本和环境：
前置条件：
操作步骤：
预期：
实际及证据链接：
影响：
责任人和预计修复时间：
修复 PR / commit：
复测人、时间和结果：
```

权限绕过、真实数据暴露、主流程打不开、内容状态错乱、数据丢失归为阻断。不能解决时记录为阶段验收未通过；不要用截图或口头承诺关闭。
