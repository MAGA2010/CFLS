# 协作、工程和完成定义

## 一、工作方式

- A 为接口和集成负责人，B 为小程序负责人，C 为管理后台负责人；每个工作包有单一责任人，但跨端缺陷按责任端协助修复。模块职责以最新任务书为准，取代旧版 A/B/C 分配。
- 第 1 天上午开 45 分钟启动会：确定人员、开工日、投入时间、库版本、管理端/数据库环境、微信开发者工具、校方联络人；当日结束前 A 提供可编译骨架和 API 契约，B/C 并行用契约 mock 开发，mock 与服务端联调时替换为同一接口客户端。
- 每日两次同步：上午报告当天交付和接口依赖，晚上在 Issue 发可核验代码/PR、测试结果、阻塞、次日计划。阻塞半天以上直接通知负责人，不等待例会。
- 所有功能从默认分支拉独立分支 `feat/a-*`、`feat/b-*`、`feat/c-*`；首日创建 Draft PR，至少每天推送一次。业务代码不直接提交默认分支；A 管跨端集成，但不独占评审。
- B 和 C 互审；A 的安全/接口变更由 B 或 C review；修改接口先更新契约并通知依赖者；任何人在自己 PR 上不可充当唯一评审。PR 以可审查的小批次合并，第 3 天起持续集成。

## 二、PR 必填内容

关联 Issue、目标和范围、设计选择、API/数据库迁移与兼容性、权限影响、依赖与环境变量变更、执行命令与真实输出、失败/未执行原因、截图或录屏、回滚方法、已知问题、审查人。涉及数据库结构必须同时提交迁移、回滚或向后兼容方案以及测试数据变更。保留代码审查反馈；失败 CI 不得标为通过。

## 三、技术默认值

默认单仓库 TypeScript：小程序 `apps/miniapp`（uni-app + Vue 3）；管理后台 `apps/admin`（Vue 3 + Vite）；服务端 `apps/api`（Node.js + NestJS 或团队熟悉的 TypeScript HTTP 框架）；PostgreSQL；`packages/contracts` 放经版本管理的 OpenAPI、类型与示例；Docker Compose 提供本地/测试环境。A 第 1 天确认具体版本、包管理器、架构决定和锁文件。若无法验证微信构建，当天提出替代方案并记录，H5 截图不能代替小程序验证。不要为架构复杂度而拆微服务；本阶段单体服务即可，但职责、接口和环境分离。

仓库目录是目标，不代表已实现。保持依赖可复现、格式和静态检查统一；环境变量提供 `.env.example`，绝不提交真实 `.env`、密钥、真实学校资料、数据库备份或编译产物。限制依赖数量与授权，锁定版本。

## 四、完成定义 Definition of Done

每个工作包要同时满足：

1. 功能符合任务书和接口契约，正常、空、失败、权限及重复操作有明确行为；没有伪造完成的按钮。
2. 每个权限或状态变化在服务端强制校验；前端隐藏按钮不能替代后端校验。测试与 API 文档同步更新。
3. 本地和 CI 命令可执行；提交与功能风险相称的自动化测试，并记录手测设备与结果；未测试不得声称通过。
4. 有 README、数据迁移/种子、环境要求、访问方式、故障处理、对已有功能的影响及已知问题；本地运行无需个人私有路径。
5. 经另一名成员 review，解决阻塞问题后合并；第七天在最终 commit 和干净环境重新验证，证据可追溯。

## 五、内容和数据

测试环境只使用明确标记的合成账号、合成学校内容与虚构咨询数据，不能使用学生、家长、教师真实信息。数据、图片、校名、费用、学校成果须校方审定后才能发布。默认公开用户端只返回已发布内容；草稿、审核记录、联系方式或测试数据不能被匿名用户查询。后台界面须显示当前环境与角色。咨询端到端流只接受标记为测试用途的虚构数据；生产环境默认关闭咨询提交，直到校方批准和生产门槛通过。

## 六、需求与版本管理

P0 是共同约定的演示候选版硬门槛；P1 是优先补齐能力，时间不够须明确登记并由负责人确认；后续为生产条件与扩展。变更用 Issue 写触发原因、范围、验收变化、负责人、工期影响，由负责人确认。阶段未达成时只能报告失败或阻塞，不得修改验收表掩盖问题。
