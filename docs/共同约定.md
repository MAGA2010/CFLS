# 共同约定与技术契约

## 1. 目标和边界

交付可以从干净环境运行的微信小程序内部演示版，7 天按实际开工日起算。所有内容、数据、通知、报名和后台操作默认本地演示，不连接生产服务，不接收真实家长和学生信息。没有真实后端时，UI 必须明确显示“演示数据／本地模拟，不会发送或保存真实报名”。

## 2. 默认技术路线及首日决策

默认选团队熟悉的 uni-app + Vue 3 + TypeScript，目标编译到微信小程序；依赖锁文件入库。A 在第 1 天上午创建最小工程并与 B、C 一起验证：安装依赖、构建微信产物、用微信开发者工具导入并打开两个页面。如果开发者工具、AppID 或依赖不可用，立即记录阻塞，负责人当天决策可用的本地预览或替代框架；不得把 H5 预览当作已验证的小程序。采用其他路线须在 README 写出决定、命令和影响。

仓库当前为空，下面是**建议目录，不代表已经存在**。A 在第一天冻结实际路径并通知 B、C；多人并行开发时，尽量只修改各自目录。

```text
src/
  pages/                 页面，按 home / school / academics / outcomes / campus / news / admissions 等分目录
  components/            公共组件（A 管理），模块私有组件放模块目录
  data/                  演示内容与种子数据，按模块划分
  services/              数据读取接口和演示实现
  types/                 共同类型
  styles/                字体、颜色、间距、通用样式
  assets/                自制或授权可公开资源，不含未授权校徽和照片
docs/                    决策、测试、运行和交付记录
```

框架实际生成目录不同则以 A 记录的真实路径为准；禁止为满足目录示例而破坏框架约定。A 独占路由注册、全局配置及公共样式的合并；B/C 以独立 PR 提出变更。A 在 1 天内提供可运行的路由和组件示例，B/C 可用本地临时模块继续，不等所有首页效果完成。

## 3. 页面与数据契约

路由语义由 A 与 B/C 共同冻结：home、school、academics、outcomes、campus、student-union、news-list、news-detail、admissions、contact、demo-form、demo-admin。具体路由路径以实际路由表为唯一依据。入口不允许指向空白页；缺内容时展示“内容待学校确认”和返回入口。

第 1 天对齐并提交 TypeScript 类型或等价数据契约，至少涵盖：

```ts
type ContentStatus = 'draft' | 'published';
type ContentItem = {
  id: string; title: string; category: string;
  summary: string; body: string; publishedAt?: string;
  cover?: string; status: ContentStatus; isDemo: boolean;
};
type PageSection = { id: string; heading: string; body: string; image?: string; isDemo: boolean };
type ServiceResult<T> = { ok: true; data: T } | { ok: false; message: string };
```

字段可由 A 根据框架调整，但必须写明并兼容 B/C。种子数据是明确标识的虚构示例；列表与详情依据稳定 id 对应，找不到 id 显示可返回的空状态。日期排序规则、图片缺省、空集合、查询失败、同步或异步接口由 A 在契约中说明。

内容统一通过 service 读取，不能把关键数据散落在页面；演示后台保存草稿、发布后须反映到前台列表或详情。首期只需要本机本地存储，A 定义 seed 合并和重置规则。发布状态只是一台设备内的演示状态；不得声称具备线上审核、用户鉴权或多端同步。

## 4. 设计与可访问性

以移动端为主，统一字号、颜色、间距、按钮、卡片、页面标题、空状态和加载状态；文本对比清楚，重要信息不得只靠颜色区分。所有可点击元素需有足够触控面积、可读标签和清晰反馈；图片提供有意义的说明或替代信息。开发者工具至少测试 375px 和 390px 两个宽度及长文本、无图片场景，真机有条件时补测。禁止虚构学校统计、政策、联系方式、师生评价或版权授权。

## 5. Git 与协作

- 从默认分支拉取；功能分支命名 `feat/a-*`、`feat/b-*`、`feat/c-*`，不要直接向默认分支推送业务开发。
- 首日建 Draft PR，关联任务 Issue；每日至少推送一次可读提交。合并前同步默认分支，解决冲突；锁文件改动需注明原因。A 负责最终集成，B/C 各评审对方至少一个 PR；自身 PR 不自审。
- 提交说明建议 `feat: ...`、`fix: ...`、`docs: ...`；每次改动范围清晰，不提交构建产物、依赖目录、真实数据、账号或密钥。
- PR 必填：做了什么、对应任务、运行/测试命令和结果、截图或录屏、已知问题和影响、手动验收步骤、是否引入依赖。实际未运行就写未运行及原因；不要把 AI 生成的结论当证据。
- Issue 每日写：完成内容、提交或 PR 链接、验证证据、下一步、阻塞及需要谁在何时决策。安全或个人信息问题不要贴出真实数据。

## 6. 模拟表单契约

C 完成咨询/活动报名交互。初稿只使用“演示姓名”“演示联系方式”等虚构输入，界面明确禁止真实信息。表单只在内存中处理：校验通过后显示模拟成功，不发送网络请求、不写日志、不写本地存储；刷新或离开后清空。失败要说明原因，重复点击期间禁用提交。只用必要演示字段；真实收集前需学校确定字段、告知与同意、存储、权限和处理流程，另行实施。

## 7. 范围决策

P0：可运行工程、核心栏目与 25 项映射、导航、新闻详情、模拟咨询、模块集成、无严重缺陷、交付文档。P1：演示后台、搜索筛选、日历、活动模拟报名、基础 CI、品质优化。P2：更多动画、多语言、地图 SDK、真实微信授权、正式 CMS、推送、真实报名与支付。7 天内优先完成 P0，再做 P1；若时间紧，负责人可缩减 P1，但必须记录变更和未完成事项。P2 不应挤占基本验收。
